# 分阶段实施方案（设计修订，尚未实现）

## 执行原则
本地开发与 ChatGPT 在线验收分开。使用内置本地工具完成开发，不要求先连 OmniTool；每次实际本地/远程任务仍按 CONTRACTS.md 核验目标和权限。除非明确追加需求，不自建 MCP Server，不实现新权限引擎。
每批先列文件与范围、记录基线，再修改、检查和审查；无 Git 时保留原文、哈希与 unified diff，不自动初始化或提交仓库。

## P0 两类预检
- P0-L 本地开发：核对实际路径、内置工具读写权限、已有文件、Git 是否存在及可用运行时。只读探测不要求安装依赖或登录。目标不符即 BLOCKED；Git 缺失使用快照差异。
- P0-H 在线宿主：记录账户可用界面、插件发现、工具暴露、目标设备/目录、授权与最小读取。只能由目标 ChatGPT 会话的真实结果证明。
- 浏览器会话核验仅阻塞浏览器验收；App 绑定仅阻塞绑定版，不阻塞本地索引和 Skills-only 包。

## P1 固定来源与最小数据集
依赖：P0-L；不依赖 P0-H。
- 固定上游 commit，核对许可、真实目录与解析规则；按 SOURCE_MAPPING.md 保留双标识。先验证来源再复制，禁止执行上游脚本中的未知命令。
- 开发侧完整目录用于发现和引用完整性检查；发布包按验收批次包含 ROLE_COVERAGE.md 中已验证的精选角色和引用闭包，不再以五类为总上限。未打包角色应明确 unavailable，不依赖联网补齐。
- 交付索引生成脚本、agent-catalog.json、upstream-lock.json、精选原文及许可/出处，全部角色资料与 SHA、哈希一一对应。
- 单测多行 Frontmatter、转义、重复身份、缺源文件、路径逃逸、无效引用、可重复生成。完整 Runbook roster 校验属于开发侧；仅把 V1 使用的引用闭包打包。
- 验收：真实单测输出和固定输入产生相同目录/内容哈希；未审清许可不得进入分发包。

## P2 Skills-only 候选包
依赖：P1；不依赖在线注册或 App 绑定。
- 创建 portable plugin.json、唯一 agency-workflow/SKILL.md、精选 references，以及轻量打包和契约检查；固定 schema 来源/版本/哈希，不以字段存在检查代替 schema 校验。
- Skill 明确 Agency Agents 角色编排的触发边界；普通单一修复/审查请求优先现有专用 Skill。没有可加载的外部 Skill 时按本 Skill 的阶段交接规范使用实际工具。
- 只复制允许清单到独立构建目录；拒绝越界路径、软链接逃逸、Windows 大小写重名、缺引用、凭证与私人路径；保留上游许可和归属说明。
- 交付 build/plugin/、ZIP、内容清单和 SHA256；生成物和原始日志不提交。验证 ZIP 根结构、唯一 Skill、引用闭包及无 .app.json/apps。
- 自动化只能证明包契约与路由样本规则；实际 Skill 激活不能由字符串匹配测试证明。
- P2 完成只称候选包可供安装验证，不称已安装。

## P3 私人插件只读闭环
依赖：P2 + P0-H 的读取能力；不依赖可选 App 绑定。
- 从实际安装副本开启新会话，记录包哈希/版本、宿主界面和可用工具。
- 验证直接/间接编排请求、应不触发的普通单任务，以及缺工具/权限/错误目标的阻断行为。
- 读取指定测试项目并给出来源证据，确认无业务文件修改。只读完成条件见 CONTRACTS.md。
- 验收：真实 Skill 加载/触发与工具读取证据，不用 Codex 本地结果替代 ChatGPT Web 结果。

## P4 受控修复与审查
依赖：P3 + 本次写入授权。
- 在专用 fixture 和明确路径内修复一个 Bug，预先列测试输出目录；保留原有改动。
- 交付任务交接记录、实际补丁/差异、测试和只读审查；默认同一会话角色化阶段，独立 Agent 只有宿主真实支持且获授权时才单列。
- 正常用例通过，测试失败、范围扩大和副作用不明时按契约退出；不靠模型自评覆盖失败。

## P5 浏览器与对照评测
依赖：P3 + 浏览器预检；全量对照评测还依赖 P4。
- 使用测试站点记录真实 UI 结果、快照/日志，保留失败与未执行项。
- 12 场景按 TEST_PLAN.md 分层评估；发布能力涉及的所有必需/安全项必须通过，10/12 只作为补充效果指标。
- 固定 fixture、模型、权限、工具与提示词；插件启用/禁用各至少三轮，报告逐次结果、中位数与异常；无足够样本不声称统计优势。

## P2-B 可选 App 绑定版
依赖：Skills-only 包契约通过 + P0-H 真实注册证据；不是 P3 前置。
- 使用平台导出的映射并核对 schema/宿主；不按前缀猜 ID。生成独立绑定包，验证 .app.json/apps 成对、required 依赖缺失会阻断。
- 单独验收安装与权限；Skills-only 成功不代表绑定版成功。暂不需要时标记 DEFERRED，不阻塞首发。

## P6 超出本轮范围的扩展决策
用户已授权扩展至完整研发流程的 18 个角色，按下文 P7–P9 分批实施。超过该目录的专项角色、额外上游 Runbook、常驻调度或 MCP，仍须在需求和评测证据支持后扩展；TEAM-14 的轻量检查点与恢复属于本轮必做，不受该扩展条件阻塞。先记录 ADR、缺失能力、代价、失败路径、验收及回退方式。

## 分级交付
- 文档设计完成：方案与检查记录；不代表代码完成。
- 候选包完成：P1/P2 本地契约通过；不代表宿主安装或实际触发。
- 只读试用：P3 及其必需安全场景通过，仅声明只读能力。
- 修复能力：P4 及相关失败路径通过。
- 浏览器能力：P5 对应 UI 与安全项通过。
首发默认 Skills-only；每个能力按实测状态发布，未验收功能明确禁用/未验证。App 绑定、浏览器和全部 Runbook 不作为只读试用的强制前置。

## P7–P9 完整研发阶段（最终必做，实施 TODO）
- P7：依赖 P3 和 P1/P2 对新增角色的来源、许可、索引、引用与路由验证；接入产品、计划、UX/UI、系统架构、后端及数据库角色。通过需求到前后端/数据库变更的教学项目验证 ROLE-03–10，缺输入时停止或明确假设。
- P8：依赖 P4/P5（UI 用例适用时）和 P7；接入自动化测试、API测试、安全和证据验收角色，结合既有 Reviewer 验证 ROLE-11–15；安全扫描限授权 fixture，失败必须阻断。
- P9：依赖 P8；接入 DevOps、SRE、Technical Writer；测试环境演练候选版本构建、部署、回滚、告警、恢复与文档上手，验证 ROLE-16–18；生产发布必须另行显式授权。
- Orchestrator/Onboarding 的 ROLE-01/02 随 P3 验证；所有批次都记录交接、跳过理由、工具结果与权限。完整流程验收不能仅凭角色存在或旧版 12 场景通过。
- 本地批次测试不等于宿主真实触发；每批更新候选包并在目标会话验证新增场景。失败时停止开放该能力，保留已验证能力和用户已有修改。

## 顺序、失败与最终出口
- 推荐顺序：P0-L → P1/P2候选 → P0-H/P3/P4/P5执行基础 → T-01/T-02 → T-03–T-07（结合P7–P9）→ T-08/T-09。T-01契约与fixture可在本地基础就绪后提前准备，无需等待在线注册。
- 所有工作包同步契约、失败路径、自动化检查、实际宿主证据及文档；具体实现仍先列授权范围和当前基线。
- 每包失败保留证据并停止依赖任务；重新诊断后有限修复，不重复非幂等动作。继续使用已通过的能力但不得宣称全团队完成。
- 最终交付：完整候选包、所有团队入口/流程/模板/校验、角色来源与许可、教学环境与测试、操作/恢复文档、完整需求追踪和四条综合E2E证据。只读 MVP 和 P9角色场景通过均不能代替 T-09。
