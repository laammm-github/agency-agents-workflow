# 完整研发团队功能规格与验收

## 1. 最终交付目标
用户要求实现完整研发团队功能。18 个角色只是知识与职责资源，角色齐全不构成功能完成。最终产品必须能在获授权的项目中组织并完成需求到交付、运维反馈的工作，包括管理工作项、执行、验证、记录和恢复；不得以角色说明书、提示词演示、只读 MVP 或单个 Bug 修复代替最终交付。
本规格是功能与最终验收范围的权威来源；ROLE_COVERAGE.md 管角色来源/职责，CONTRACTS.md 管字段/状态，IMPLEMENTATION_PLAN.md 管实施依赖。v2 记录、门禁与恢复辅助脚本已实现并通过本地回归，完整宿主验收仍未完成；逐项证据见 ACCEPTANCE_MATRIX.md，不以实现或打包代替最终通过。目标覆盖通用 Web/服务软件；专项技术栈可扩展，但不能借按需加载跳过适用的必需团队能力。

## 2. 功能清单（全部属于最终必做范围）
每项同时要求可操作流程、可保存产物、正常/失败路径、自动化契约检查和真实宿主验收。TEAM 用例与 ROLE 用例不同：前者证明团队功能，后者证明角色适配。

| ID | 团队功能与责任 | 必须交付的行为和产物 | 正常验收 | 失败路径与退出条件 |
|---|---|---|---|---|
| TEAM-01 | 项目接入与能力核验；Orchestrator/Onboarding | 接入新建或已有项目，记录设备/目录/工具/授权/基线；列出能力缺口 | 两种项目均读到真实源码或授权创建项目骨架并核验 | 错误设备/目录/缺工具阻断对应任务，不能用别处结果替代 |
| TEAM-02 | 需求与范围管理；Product Manager | 问题澄清、用户故事、验收项、非目标、优先级、版本化需求和变更单 | 用户需求可追踪到任务和验收 | 必需业务决策未确定时提出具体问题并阻断依赖项，不把假设当确认 |
| TEAM-03 | 计划与任务管理；Project Manager/Orchestrator | 建立 backlog、依赖、责任角色、里程碑、状态、风险与进度；执行下一个可运行任务 | 跨前后端任务按依赖推进，状态来自产物和证据 | 检测循环依赖、无责任人、缺产物和阻塞；状态不被自然语言虚报覆盖 |

| TEAM-05 | 技术方案与契约；Software/Backend Architect | ADR、模块边界、API/schema、兼容性、数据方案和测试策略 | 前后端按同一版本契约开发 | 未解决的关键冲突阻断实现；契约变更使下游验收失效并触发重验 |

| TEAM-07 | 测试与缺陷闭环；开发/自动化/API测试 | 单元/契约/集成/E2E、适用的性能和可访问性检查；缺陷复现、分级、关联修复和回归 | 植入 Bug 被发现、修复、回归，并保留前后证据 | 缺环境记 BLOCKED，失败/不稳定/未跑不能计作通过；重开仍可复现的缺陷 |
| TEAM-08 | 代码与安全质量；Reviewer/AppSec | 代码审查、威胁模型、依赖/秘密/越权检查、修复验证与例外记录 | 植入逻辑回归和安全缺陷阻断交付直至修复 | 高风险或必需检查未通过不可被 Developer 自评、评分或普通用户口头放行静默清除 |

## 3. 典型操作入口
唯一 agency-workflow Skill 支持自然语言：启动项目/迭代、梳理并执行计划、执行下一项、查看状态与阻塞、变更需求、报告并修复缺陷、准备发布、执行已授权发布/回滚、排查事件、生成交接、保存进度/继续项目。
这些是工作流操作入口，不是假定宿主具备的工具名。每个入口读取最少资料和当前项目状态，实际动作必须调用已暴露且授权的工具；各入口的宿主验证状态见 ACCEPTANCE_MATRIX.md。不新增同名工程 Skills，不重造工具执行器。

## 4. 协作和执行方式
默认单会话按角色顺序执行，保证任务责任、交接和质量门禁；团队功能不依赖虚构的独立进程。若将来用户要求并行/独立审查，须另验宿主能力和授权，不能把顺序角色化阶段冒称独立团队进程。
在已授权范围内连续推进所有可执行工作；仅在缺关键输入、权限不足、门禁失败或外部状态不明时停止相应依赖。需求确认、设计批准、上线决定分别记录，已有有效授权无需反复询问。
状态记录是项目产物，执行器仍是宿主工具。轻量 JSON/Markdown 检查点与确定性校验脚本属于必做实现；不需要自建常驻调度、数据库租约或 MCP Runtime。

## 5. 端到端综合验收（全部必过）
- E2E-TEAM-A 新建项目：授权空目录 → 需求/设计/计划 → 前后端/API/数据库实现 → 测试/缺陷/审查/安全 → 固定候选构建 → 授权测试环境部署/冒烟 → 文档交接。
- E2E-TEAM-B 已有项目迭代：保留原有修改 → 建立基线 → 中途变更接口需求 → 更新契约/任务/代码/测试/文档 → 缺陷修复与重新验收 → 输出追踪链。
- E2E-TEAM-C 发布与事故：同一构建物部署 → 注入可控故障 → 日志/指标发现与定位 → 授权回滚/恢复验证 → 复盘/文档 → 下一轮 backlog。
- E2E-TEAM-D 中断恢复与阻断：执行中断/连接失败 → 新会话读取检查点 → 发现外部修改与未知副作用 → 核实而非重放 → 在授权范围继续；覆盖未授权发布、失败测试、越权输入和缺证据拒绝就绪。
每条保留实际工具记录、退出码、前后差异、版本标识、交接、测试和验收报告。教学环境不能替代真实宿主的工具可用性验收，但无需操作生产系统才能验收流程。

## 6. 项目最终完成定义
TEAM-01–14、ROLE-01–18、四条综合验收及包/权限门槛全部有证据并通过。条件性检查须有适用性依据，通用团队功能不能整体标记 NOT_APPLICABLE 来规避实现；外部设施缺失则最终验收 BLOCKED，而非默默删除需求。
只读 MVP、角色索引、候选 ZIP、局部场景通过均是中间里程碑。产品只承诺已实测的平台/项目类型；无人值守、常驻后台与所有专项技术栈不是本轮隐含能力。完整功能实现仍须使用用户授权的真实工具，不降低完成标准。
